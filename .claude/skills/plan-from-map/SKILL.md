# 从思维导图排开发

## 这张图是什么

`PLAN-MAP.md` 是 noone 手写的**全景思维导图**（普通 Markdown，标题层级 = 分支）：

- `PLAN-MAP.md` — 全景：谁在用、主流程、系统分几块、数据怎么串、页面地图、做到哪、阶段顺序、**我要加的模块**、等拍板的问题。
- `PLAN.md` — 任务清单：一行一条待办，带 `[ ] / [?] / [~] / [x]`。
- `PROJECT-ARCHITECTURE.md` — 架构与产品基线，**架构变更的审批规则在这里**。

图是意图，`PLAN.md` 是队列。图变了，任务队列要跟着变；任务做完了，图上的状态要跟着改。

## 什么时候用

- noone 说「按图安排开发」「我加了模块」「把想法拆成任务」。
- 每次开工选 task 前，用它确认全景与当前阶段（见 `PHASES.md`）。
- 一段工作收尾时，用它把 `[~]` 落成 `[x]`、把新发现写成 `[?]`。

## 状态标记的读法

| 图上的标记 | 含义 | agent 该做什么 |
| --- | --- | --- |
| `[x]` | 已有 / 已做完 | 只当背景，**不重做**；发现与代码不符就报偏差 |
| `[~]` | 正在做 | 先查分支和 PR，**接着做**，别另起一条 |
| `[ ]` | 想做、还没开始 | 可挑，先拆成任务再动手 |
| `[?]` | 拿不准，等 noone 拍板 | **攒着一次问清**（见下），不要自己定标准 |
| `[新]` | 新想法，没评估 | 先做可行性判断和影响面，再问要不要排期 |

## 怎么做

1. **先读，不改代码。** 读 `PLAN-MAP.md` 全文 → 读 `PLAN.md` 待办 → 读 `PHASES.md` 判断现在是开发阶段还是维护阶段。
2. **对齐差异。** 图上写的 `[x]` 若在代码里找不到，或代码里已有但图上没有，先列出来，不要默默改图。
3. **把 `[新]` 的模块拆成任务。** 每个模块至少回答四件事，写进 `PLAN.md` 的任务描述：
   - 给谁用（哪个角色、哪个场景）
   - 解决什么痛点（对照 `PRODUCT.md` 的产品原则）
   - 落在 核心 / 插件 / AI 哪一类（三类边界见 `PROJECT-ARCHITECTURE.md` §1）
   - 验收怎么算过（可观测的结果，不是「做完了」）
4. **分类，别抢跑。**
   - 纯展示、纯前端、已有插件内的小改动 → 可直接排期。
   - 碰 **模块边界 / 数据模型 / 权限 / 插件归属 / 模板体系** → **先写提案给 noone 批**，`PLAN.md` 里标 `[?]`，不写代码（`AGENTS.md` 红线）。
   - 涉及扣积分 → 先读 `.claude/skills/verify-credit-ledger/SKILL.md`，动完必须过它的检查。
   - 涉及点位图保存 / 草稿并发 → 先读 `.claude/skills/verify-point-map-save/SKILL.md`。
5. **回写给图。** 排完期，把 `PLAN.md` 里已经明确的项，在图对应分支上把 `[ ]` 改成 `[~]`；做完改成 `[x]` 并挪去 `WORKLOG.md`。**改图只改状态标记和新增分支，不要重写别人的措辞。**
6. **交接。** 一个任务一个分支一个 PR，PR 里写明「来自 PLAN-MAP 的哪一支」。开发与验收分离：写代码的 agent 不能自己宣布通过。

## 问 noone 的规矩

- `[?]` 的问题**攒起来一次问清**，别边做边刷屏（这已经是仓库里的约定，见 `PLAN.md` 文末）。
- 每个问题给 2–3 个选项 + 你推荐哪个 + 为什么，别问开放式问题。
- 架构类问题不问就直接做 = 违规，即使看起来很小。

## 图的渲染（可选）

`PLAN-MAP.md` 本身就是源码。要看可折叠的图（只在本地看，HTML 不入库）：

```bash
npx markmap-cli@latest PLAN-MAP.md -o plan-map.html --no-open --offline
```

`--offline` 把依赖内联，产物可离线打开。`plan-map.html` 是构建产物，不提交。

## 不要做的事

- 不要把图当数据库去同时编辑：`PLAN-MAP.md` 是 noone 的主场，agent 只做「回写状态」这一种修改。
- 不要把 `[新]` 直接当已批准的需求开工。
- 不要为了对齐图去改架构；图服从架构基线，不是反过来。
