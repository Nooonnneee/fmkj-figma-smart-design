## 甲、桌面客户端：项目默认存本地

### 修改前

客户端（`desktop/`，Electron 45）是一个**纯外壳**：`desktop/src/main.js` 用 `BrowserWindow` 加载
服务器上的 `/projects`，所有数据、渲染、打印都在服务器。本地只存三样东西（`desktop/src/store.js`）：
窗口位置、服务器地址、会话文件。

`desktop/src/preload.js` 只暴露 5 个能力（版本、更新、设置、外链、重试），**没有任何数据能力**。

项目必须登录服务器才能存在。

### 修改后（2026-11-15 noone 重新定了口径：**上传即搬家，不是同步**）

项目有且只有一个**权威副本**，位置二选一：

| 状态                           | 权威副本在哪                | 本机有什么                    | 谁能打开                  |
| ------------------------------ | --------------------------- | ----------------------------- | ------------------------- |
| **本地（默认，新增）**         | 客户端 `userData/projects/` | 就是这份（可编辑）            | 只有这台机器              |
| **云端（新增上传，或老项目）** | Postgres `projects` 集合    | **只读缓存**（离线看/打印用） | 同账号任意设备 + 分享链接 |

**「上传到云端」= 搬家，不是复制一份两边同步：**

- 上传成功后，这个项目此后**所有编辑都直接写云端**，本机不再保留可编辑副本。
- 因此**不存在「两边都改了要合并」这件事** —— 这是 noone 这条口径最大的价值，整类冲突合并问题消失。
- 本机保留的只读缓存**不参与编辑**，只用于：断网时看项目、断网时打印（第 2 条要求）。
- 断网且项目在云端时，界面必须明确「当前离线，只能看和打印，不能改」，不要让人写完才发现存不进去。

新建项目默认落「本机」。本机项目顶部常驻「仅存于此电脑」+「上传到云端」按钮（后者要登录且已注册账号）。
上传前弹一次确认，讲清两件事：① 上传后再改就是改云端那份；② 云端项目在断网时只能看不能改。

### 为什么「打印也要能离线」是最贵的一条

这是本提案的核心成本，必须说清楚：

- 打印页（`src/app/(frontend)/print/**`，10 条路由）是 **Next.js 服务端组件**，靠
  `appAuth` + `getPayloadClient` + `getCatalog` 在服务器上取数据并渲染 HTML。
- 报价单（975 行）、点位图、交底清单、采购单、方案演示、合同，全部如此。
- 「导出 PDF」本身是**浏览器端**做的（`src/lib/export-pdf.ts`，`print-toolbar.tsx` 是
  `'use client'`，用 canvas 拼页），所以渲染成 PDF 那一步不需要服务器——**需要服务器的是
  「先有那个 HTML 页面」**。

推论：要离线打印，**必须让这 10 条打印路由在本地也能出页面**。三条可选路径：

| 路径                      | 做法                                                                                                                                 | 代价                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **B1 本地服务**           | 客户端内置一份 `output: 'standalone'` 的 Next 服务（`next.config.ts:126` 已经是 standalone），用本地库当数据源，打印页打 `127.0.0.1` | 大：要打包 Node 运行时、管端口、管进程、管升级；安装包显著变大                                   |
| **B2 打印页改客户端渲染** | 把 10 条打印路由重写成能在浏览器里跑（数据从本地读，组件已是纯 React）                                                               | 中：10 个页面都要改，且要保证和服务器版视觉完全一致；方案模板 `deck/` 已无服务端依赖，可行性较高 |
| **B3 离线只出「简版」**   | 离线时只给报价单 + 点位图两样，其余提示需联网                                                                                        | 小：但和「打印也要能离线」不完全一致                                                             |

**我的建议原本是 B2。noone 2026-11-15 已拍板走 B1（客户端内置）**，所以下面按 B1 重估。

### B1 实测结果（2026-11-15 夜里真跑过，不是估算）

上面那条「要打包 Node 运行时」是**错的方向**：Electron 自带 Node，不需要另带。真正要验证的是
「本地库能不能冒充线上那个 Postgres」，以及「打包后到底多大」。两条都实测了：

**① 本地库：用 PGlite（Postgres 18.6 编译成 WASM），不用重写任何迁移。**

- 把 14 个真实迁移文件全部跑在 PGlite 上：**14/14 通过**，最慢 183ms，总计约 0.4 秒。
- 迁移里用到 `DO $$ ... $$`（plpgsql）、`gen_random_uuid()`、`jsonb`、`text[]`、复合外键、级联删除，
  PGlite 全都支持。全库没有 `CREATE EXTENSION`、没有 `CREATE INDEX CONCURRENTLY`，两个 PGlite 的短板都没踩到。
- 用真实 Payload 跑增删改查：`create` / `find`（带 where 条件）/ `update` / `delete` / `count` 全通。
- **起真实服务验过**：`next build` 出来的 standalone 指向 PGlite，登录后打开
  `/print/quotes/<id>` → **HTTP 200，49261 字节，页面里确实渲染出了刚写的报价标题**。
  这是「B1 真能出打印页」的端到端证据，不是推断。
- 数据目录：空库跑完 14 个迁移后 **50MB**。
- 体积：`pglite` 26MB（未压缩）+ `pglite-socket` 0.4MB，**零原生模块**（纯 wasm），所以不用按平台重编。

**② 安装包：从 116MB 涨到约 250–280MB。**

- 现在：mac arm64 115MB / mac x64 121MB / win exe 116MB。
- 要加进去的运行时（实测）：`.next/server` 142MB + `node_modules` 86MB + `public` 17MB +
  `src/migrations` 7.3MB ≈ **250MB 未压缩**；Electron 安装包本身是压缩的，实际增幅大约 **+140~160MB**。
- 顺带发现：`promotion-kit`（105MB 的宣传样张）被 Turbopack 的「动态文件访问」追踪**误打进了 standalone**，
  `docs/`、`e2e/`、`desktop/` 也在里面。做 B1 时必须用 include 白名单裁掉，否则等于白送客户 100MB 废文件。
  这笔钱现在是**白花的**，裁掉后安装包能省下这部分的压缩体积。

**③ 唯一新增的运维负担：管进程。**

- 客户端要起两个进程：PGlite socket（本地 Postgres 端口）+ `node .next/standalone/server.js`。
  两个都监听 `127.0.0.1`、用随机空闲端口，不能写死。
- 退出、崩溃、升级都要把子进程收干净；用户强杀主进程时会留孤儿进程（要在下次启动时按 pid 文件清理）。
- 端口冲突、防火墙弹窗、杀毒软件误报 —— 这三样是 Windows 客户端的经典客服来源，**必须提前写进已知代价**。

**④ PGlite 的并发是有限制的，别踩。**
默认只允许 **1 个连接**，Payload 的连接池会直接报 `Connection terminated unexpectedly`。
实测把 `maxConnections` 调到 10 后，10 个并发事务 **10/10 成功**。
所以：**必须显式配置 `maxConnections ≥ Payload 连接池上限`**，并且这条要写成代码注释，不然下一个人一定会踩。

### 按 B1 重估的工作量

| 块           | 内容                                                     | 相对 B2                                    |
| ------------ | -------------------------------------------------------- | ------------------------------------------ |
| 本地库接入   | PGlite + socket + 迁移自动执行 + 连接数配置              | 新增，但**已验证可行**，不是风险项         |
| 服务进程管理 | 启动/退出/崩溃/孤儿清理/端口选择                         | 新增，**这是 B1 比 B2 多出来的主要复杂度** |
| 打包裁剪     | 白名单裁掉 promotion-kit / docs / e2e / desktop          | 新增，顺带省 100MB                         |
| 打印页       | **不用改**（10 条路由原样在本地跑）                      | 比 B2 **省掉** 10 个页面重写               |
| 数据迁移     | 本地项目 ↔ 云端项目两套库结构（同一套 schema，不同实例） | 新增                                       |

**结论：B1 比我原来的估计便宜，但没有免费。** 省掉的是「重写 10 个打印页」这件最容易出错的事
（视觉不可能和服务器版完全一致），换来的是「管两个子进程」这件运维上的脏活。
考虑到打印排版是客户直接拿去给业主看的，**视觉一致比进程管理重要**，B1 这个选择是对的。

### 数据迁移 / 兼容

- 老客户升级后，已有云端项目**不受影响**，仍走云端（客户端打开时列出云端项目，本机缓存一份只读）。
- 本地项目第一次上传时生成新 id，**不做双向同步**（口径 7 已取消这件事）。
- 上传成功后本机的可编辑副本**转为只读缓存**，不是简单删掉——直接删是不可逆的，且断网还要靠它。
  界面上告诉客户「这份已经是云端的了，本机这份只用来离线查看」。
- 云端项目在本机首次打开时就缓存；缓存按项目 id 存，可被服务器新版本覆盖。

### 一个必须提前处理的老问题：线上已有项目

2026-11-15 查过线上生产库（`fmkj`）：**51 个项目 / 15 个用户 / 728 个产品 / 76 份报价**。
这些项目现在都在云端。改成「默认存本机」以后：

- 老用户打开客户端，**默认视图是本机项目列表 → 空的**。
- 如果不做处理，客户会以为项目丢了 —— 这会直接变成客服事故。

所以客户端首屏必须**同时显示两个来源**（本机 / 云端），而不是「本机为空就显示空列表」。
这条不是可选项，是本次改动的准入条件。

### 回滚方式

客户端功能开关（`app-config.json` 加一个 `localProjects: false`）即可让客户端退回纯壳行为，
不需要回滚服务器代码。已产生的本地文件留在客户机器上，不主动清理。

### 已知代价（客户会遇到的）

1. **数据丢失风险转移给客户。** 现在有每日 `pg_dump` 备份；本地项目没有。建议至少在客户端里
   保留最近 N 个版本快照，否则「硬盘坏了 = 项目没了」会成为客服成本。**（仍未拍板，见待答第 2 条）**
2. **分享链接对本地项目不可用。** 业主分享页 `/share/[token]` 依赖服务器数据，本地项目必须先上传。
3. **跨设备不可用（本机项目）。** 换电脑、重装，本机项目不会跟着走 —— 除非先上传到云端。
4. **用量不可见。** 纯本地项目不产生服务器记录，无法统计。
5. **上传是单向的、有门槛的。** 需要已注册账号并登录；本地项目不能凭空变成云端项目。

## 乙、AI 渠道配置开放给客户自填

### 修改前

- `/admin` 的「AI 设置」全局（`src/globals/AiSettings.ts`）`read`/`update` 都是
  `fieldCmsAdminOnly`——**只有 CMS 超管**能配。
- 客户完全看不到模型与渠道配置，只能用平台配好的模型。
- 密钥**只以环境变量名**存在库里（`AiSettings.ts:190-235`，`apiKeyEnv` 必须是 `AI_` 前缀），
  真实密钥在服务器环境变量里，**从不入库**。这是刻意设计，要保留这个优点。
- 模型列表通过 `getCompanyInfo()` 以 `base.aiModels` 下发（`src/lib/cached-data.ts:377`），
  即**所有人共用同一份**。

### 修改后（2026-11-15 noone 追加口径：**只在客户端开放，网页端不开放**）

- **入口只在桌面客户端**。网页（含小程序）的 AI 配置页**不出现**这个功能，成员无法在网页上配自填渠道。
- 每个成员可以有自己的 AI 渠道配置（自填 key），存在 `users.companyProfile.aiChannels`（新字段）。
- 有效模型列表 = 平台默认模型 ∪ 该成员自己的模型。
- 客户自填的 key → **加密后存库**（AES-GCM，密钥来自 `PAYLOAD_SECRET` 派生的独立密钥），
  **只有服务端能解**；前端永远拿不到明文，接口只回「已配置 / 未配置」。
- 客户自己的模型**不扣积分**（已定）。

### 「只在客户端开放」怎么落实——这条必须说清，否则等于没做

网页和客户端**用的是同一个网站**（客户端就是加载服务器的网页，`desktop/src/main.js` 的
`BrowserWindow` 打开 `https://fmkj.top/projects`）。所以「只在客户端」不能靠「换个页面」，
必须靠**服务端能分辨请求来自哪个环境**。

现状基础：客户端已在 User-Agent 里带标记
`app.userAgentFallback = ... FanmengSpaceDesktop/<版本>`（`desktop/src/main.js:515`）。

方案：服务端加一个 `isDesktopClient(request)` 判定，读 UA 里的 `FanmengSpaceDesktop/`。

**必须承认这个判定的强度**：UA 是客户端自己声明的，**可以被伪造**。所以它是「产品口径」，
不是「安全边界」。要点：

- 它的作用是**不让网页用户看到**这个入口（产品口径），可以接受被绕过。
- **绝不能**把它当成权限校验。谁真正能用自填 key，必须仍然绑在账号上（服务端看账号里有没有配
  合法的加密渠道），而不是看 UA。
- 因此：**网页端即使构造了请求，也只能用他自己账号里已经配好的渠道**——而那个渠道本身是
  合法的、加密存的、地址白名单过的。不存在越权。

### 为什么密钥不能放客户端

AI 的写操作工具（改项目、改点位、生成报价）全部在**服务器**执行
（`src/plugins/ai-copilot/tools/*-handlers.ts` 里的 `payload.update` / `payload.create` 都跑在 API 路由里）。
密钥放客户端 → 服务器拿不到 → 那套工具全部失效。所以只能是「客户填、服务器存、服务器用」。

### 影响范围

- 数据模型：`users.companyProfile` 新增 `aiChannels`（加密字段）；**不改** `ai-settings` 全局
- 权限模型：AI 设置从「只有超管」扩到「超管配平台默认 + 成员配自己的」，**两套并存**
- 计费：`billing.ts` / `reply-billing.ts` 需要区分「平台 key」与「自有 key」两条路径。
  口径已定：**走客户自有 key 的一整轮（含 AI 工具调用）零扣费**；用平台模型才按现有公式计费。
  落实方式见下「计费怎么分岔」。
- 端点：`ai-settings-endpoints.ts` 里 6 个 `isCmsAdmin` 校验需要新增成员级端点（拉模型、测渠道），
  且必须**限流**（否则成了免费代理）。**这些端点本身不做 UA 限制**——UA 只用来隐藏入口
- UI：新增「我的 AI 配置」页面，**入口按 `isDesktopClient` 隐藏**（网页/小程序不显示）
- AI 工具契约：不变（工具照旧），但「谁能用哪个模型」新增一条判断

### 安全边界（必须写进代码）

1. **地址白名单**：`normalizeCustomBaseUrl` 已要求公网 HTTPS，拒绝内网/本机地址
   （`server.ts:90` `isPrivateOrLocalHost`）。这条**必须保留并扩充**，否则客户可以让你的服务器
   去访问任意内网地址（SSRF）。
2. **代理滥用**：客户填的地址由你的服务器去请求，等于给了他们一个出网代理。必须限流 + 记日志，
   并对失败频率做熔断。
3. **密钥保管责任**：数据库从此是客户密钥的保管箱。**一次泄露 = 所有客户 key 一起完蛋**。
   这是接受本提案必须认的代价。
4. **隐私告知**：用自有 key 时，对话内容仍经过你的服务器。文档里要写明。

### 计费怎么分岔

现在的计费只有一个入口：`UsageMeter.credits()` 把「token 成本 + 工具费」加起来，最少 1 积分
（`billing.ts:107-120`），再交给 `saveAssistantReplyAndCharge()` 落账（`reply-billing.ts:39-97`）。
它**不知道**这一轮用的是谁的 key——`AiModelConfig` 里没有任何字段说明这一点。

改法按「一条判断，不在两处各写一遍」：

1. `AiModelConfig` 加 `owner: 'platform' | 'member'`（由模型来自平台 `aiModels` 还是成员
   `aiChannels` 决定，在拼有效模型列表时打上标记，不改表结构）。
